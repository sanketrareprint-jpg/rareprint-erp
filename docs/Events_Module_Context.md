# Events module — shared context

Read this before touching anything under `backend/src/events/`, `frontend/app/events/`, or the `Event*`/`Festival` models in `schema.prisma`. It exists because this module was independently built twice in one day by two concurrent Claude sessions before being reconciled — these are the decisions Sanket actually made, so a future session doesn't redo that.

## What it does

Register a customer, friend, or anyone else (`EventPerson`) with a WhatsApp number and an optional date of birth / anniversary date. On their birthday or anniversary, and on any recurring festival date, the backend renders a flyer image from a saved template and sends it via AiSensy WhatsApp to both that person and the owner's own number.

**Also (added 2026-08-28): Client Business Festival Wish Cards.** A completely separate flow — RarePrint's own B2B customers (`EventClientBusiness`, "Client Businesses" tab), not `EventPerson` and not `EventBrandProfile`. Each listed business can get an auto-generated, self-branded wish card (its own logo/name/phone/address/tagline, via `CLIENT_LOGO`/`CLIENT_TEXT` template fields) delivered to its own WhatsApp on any festival that has a `CLIENT_FESTIVAL` template assigned (`Festival.clientTemplateId`, independent of `Festival.templateId`). What RarePrint delivers is the finished image — the client business decides what to do with it (WhatsApp Status, forward to their own customers, etc.), which is explicitly out of scope here. See `docs/Events_Module_Client_Wish_Cards_Build_Prompt.md` for the full spec this was built from.

## Decisions that are NOT obvious from the code — don't "fix" these

- **One shared AiSensy campaign for everything.** `WhatsAppService.sendEventWish()` uses a single `AISENSY_EVENTS_CAMPAIGN` env var (default `events_wish_erp`) for birthdays, anniversaries, and every festival. This was a deliberate choice to minimize how many WhatsApp template approvals Meta/AiSensy requires — not an oversight. Do not split this into per-occasion campaigns without asking first.
- **Festivals recur by month/day, not an exact date.** `Festival.month` + `Festival.day` (both `Int`) are entered once and fire every year — there is no `date`/`sentAt` column. This was changed from an earlier "exact date, re-added every year" design specifically because Sanket asked for recurring records. If you see any reference to `Festival.date` or `Festival.sentAt` anywhere, it's stale — remove it.
- **Idempotency is uniform across all three occasion types**: before sending, the scheduler checks "does a `SUCCESS` `EventSendLog` already exist for this person + occasion (+ festivalId for festivals) + calendar year?" There's no per-row "already sent" flag on `Festival` itself, because that would have permanently blocked a recurring festival from ever firing again.
- **One photo per person**, reused for both their birthday and anniversary flyer — not separate photos per occasion.
- **Text rendering is sharp + SVG `<text>`**, not pdfkit. Unlike the Certificate Generator (which deliberately avoids SVG text to sidestep a fontconfig/Pango dependency on Railway), this module accepts that tradeoff because flyers are short single-line values (a name, a date) and the font bytes are embedded directly into the SVG as a base64 `@font-face` (`backend/src/events/fonts.ts`), which does not require the OS to know about the font — so it should still be self-contained on Railway. If flyer text ever renders as tofu/boxes in production, this embedding is the first thing to check, not a reason to rewrite the renderer.
- **Flyer field positions are fractions (0..1)** of the template image's own pixel width/height — not inches/DPI like `CertificateTemplate`, because a flyer is only ever a raster JPEG for WhatsApp, never printed.
- **`EventSendLog.occasionYear = 0`** is a sentinel for manual "send test" clicks — it's intentionally excluded from the real idempotency check so a test send can never block (or fake) a real scheduled send later that year.
- **The public flyer-image route** (`GET /events/flyer/:id?token=&expires=`) is unauthenticated on purpose — AiSensy fetches the image directly. Access control is the signed HMAC token (`EventsService.signPublicToken`/`verifyPublicToken`), same scheme as `BillingService`'s public invoice PDF link, reusing `JWT_SECRET`. Requires `BACKEND_PUBLIC_URL` to be set in the environment or every send silently fails with a logged reason — check that env var first if wishes stop going out.
- **Owner's WhatsApp number is hardcoded** (`919637318960`) inside `WhatsAppService`, matching the existing pattern for order-created notifications elsewhere in this codebase — not read from `SystemConfig` or any admin setting.
- **The real approved AiSensy template is named `hellomomentwishes`**, not the code's `events_wish_erp` fallback — `AISENSY_EVENTS_CAMPAIGN` must be set to `hellomomentwishes` in Railway's backend Variables or every send fails with an unknown-campaign error. Confirmed against the actual template (created + approved 2026-08-25) that it has exactly 3 body variables in this order: `{{1}}` name, `{{2}}` occasion label, `{{3}}` sign-off shown as "Warm wishes from `{{3}}`". `{{3}}` is hardcoded as `SIGNOFF_NAME = 'RarePrint'` in `WhatsAppService.sendEventWish()` (Sanket's explicit choice 2026-08-25, same hardcoding convention as `OWNER_PHONE`) — it is not a caller-supplied value, don't reintroduce a `customMessage`-style param for it. Anniversary years are folded directly into `{{2}}` instead (e.g. `"5th Anniversary"`, via `ordinalSuffix()` in `events.service.ts`) rather than using a 4th variable that doesn't exist in the real template — an earlier version of this code guessed a different 3-variable shape (years/message in `{{3}}`) before the template was actually built and approved; that guess is what got fixed.
- **Reusable brand fields, not branding baked into the template image (added 2026-08-27).** Sanket's original request showed a template with the firm's logo/name/phone/address/products in the header and footer, and asked for "every template" to carry these. Rather than requiring a template designer to redraw that branding into every uploaded background image, the firm's identity is a singleton row (`EventBrandProfile`, set once via the **Brand** tab) and a template just places `BRAND_LOGO`/`BRAND_TEXT` fields (same box/font controls as `PHOTO`/`TEXT`, plus `BRAND_TEXT.brandKey` picking which `EventBrandProfile` column to show) that pull from it at render time — see `brandValues`/`brandLogoBuffer` in `flyer-render.ts` and `EventsService.loadBrandForRender()`. Don't reintroduce a "type the firm name into each template" flow; that's the exact duplication this was built to avoid.
- **Festivals can be recurring (month/day) or one-time (`oneTimeDate`), not just recurring (added 2026-08-27).** `Festival.isRecurring` (default `true`) picks which; `month`/`day` are now nullable and only set when `isRecurring`, `oneTimeDate` (`@db.Date`) only set when not. A one-time festival is matched on full year+month+day (`EventsSchedulerService.matchesOneTimeDate`) so it fires exactly once and never again — it still goes through the same `EventSendLog`-based idempotency as everything else (no separate "sentAt" flag), consistent with the "no per-row already-sent flag" decision above. The recurring-by-default behavior from the 2026-08-25 decision is unchanged; one-time is purely additive.
- **A Devanagari-capable font was added for Marathi/Hindi flyer text (added 2026-08-27).** `'Noto Sans Devanagari'` (converted from `@fontsource/noto-sans-devanagari`'s woff2 to `.ttf` via `fonttools`, SIL OFL 1.1 licensed) joins `'DejaVu Sans'`/`'Segoe UI'` in `FlyerFontFamily`/`FONT_FILES`/`FLYER_FONT_FAMILIES` (`backend/src/events/fonts.ts`) and the frontend's `FONT_FAMILIES`. It covers Devanagari glyphs only (no Latin/digits) — verified via a real `sharp`/librsvg render that mixed Devanagari+Latin/digit text in one field still renders correctly through fontconfig's fallback substitution, so a field like "RarePrint.in 9637318960" alongside "श्रावण" is fine even though the two scripts come from different font files under the hood.
- **Client Business Festival Wish Cards are a NEW parallel system, not an extension of the Brand tab (added 2026-08-28).** The Brand tab / `EventBrandProfile` is a singleton — RarePrint's own identity, reused across every template. This feature needed one-to-many: a LIST of RarePrint's client businesses, each independently triggering its own render+send. So it's a fully separate schema (`EventClientBusiness`, `EventClientWishLog`, `Festival.clientTemplateId`, `CLIENT_LOGO`/`CLIENT_TEXT` field types, `CLIENT_FESTIVAL` template occasion type) and a fully separate code path (`EventsService.renderAndSendClientWish`/`sendTestClientWish`/`loadClientForRender`, `WhatsAppService.sendClientWishReady`, a second loop inside `EventsSchedulerService.sendFestivals()`) — not a branch bolted onto the existing person-flow methods. Do not merge these two flows; a client business is not an `EventPerson` and never goes through `renderAndSend`/`logSend`.
- **`EventClientWishLog` is a separate table from `EventSendLog`, not `EventSendLog` with a nullable `personId`.** Extending `EventSendLog` would have required auditing every existing query that assumes `personId` is non-null (History tab, the once-per-year idempotency check, the public flyer route) — a real risk to a table with production data. A parallel table with the identical shape/idempotency pattern (`(clientBusinessId, festivalId, occasionYear)` + `status='SUCCESS'`) was safer and is what got built.
- **Client wish cards are sent to exactly ONE recipient — the client business itself — never "also to the owner."** Unlike `sendEventWish` (which always also messages RarePrint's own WhatsApp as an "owner copy"), `sendClientWishReady` has no owner-copy branch — this is a business receiving a finished asset to use, not a personal wish, so an owner copy wouldn't make sense here. Don't add one without asking first.
- **A festival can have a `templateId` (own-customer flyer) and a `clientTemplateId` (client-wish-card) set completely independently** — either, both, or neither. `EventsSchedulerService.sendFestivals()` treats them as two independent branches per festival; a festival missing one template only skips that branch (logs a warning), never blocks the other.
- **`clientTemplateId` must reference a `CLIENT_FESTIVAL`-occasionType template, enforced server-side** (`EventsService.validateClientTemplateId`) — assigning a normal `BIRTHDAY`/`ANNIVERSARY`/`FESTIVAL` template as a festival's `clientTemplateId` is rejected with a 400, since that template has no `CLIENT_LOGO`/`CLIENT_TEXT` fields and would render a wish card with none of the client business's own branding.
- **This feature needs its own, separately-approved AiSensy template** (`AISENSY_CLIENT_WISH_CAMPAIGN`) — the message copy ("here's your ready-to-share wish card") is fundamentally different from `sendEventWish`'s personal "Happy Birthday" copy, so the existing `hellomomentwishes`/`AISENSY_EVENTS_CAMPAIGN` template cannot be reused. See `docs/Events_Module_Setup.md` §3.

## ⚠️ Never edit an already-applied migration file — add a new one instead

2026-08-25: `Festival.month`/`.day` were first shipped by editing `20260824090000_add_events_module/migration.sql` in place, after wrongly assuming it had never been deployed. It had — `prisma migrate deploy` checksums every already-applied migration file, and this app's `scripts/railway-migrate.js` treats a `migrate deploy` failure as a non-fatal warning (so the app keeps booting on drift instead of crashing loudly). Result: the checksum mismatch silently blocked the upgrade from ever running, production's `Festival` table stayed on the old `date`/`sentAt` columns while the redeployed code's Prisma Client expected `month`/`day`, and every Festival query 500'd with Prisma error `P2022` (column does not exist) until this was caught and fixed by a follow-up migration. `20260824090000` is restored to its original applied content; the month/day change now lives in `20260825120000_events_recurring_festivals/migration.sql`. The rule going forward, for this migration and every other one in the repo: once a migration folder has shipped, it is immutable — a later change is always a new migration, never an edit.

2026-08-27: a session almost repeated this exact mistake — it edited `20260824090000`'s `migration.sql` in place to add `isRecurring`/`oneTimeDate`/`EventBrandProfile`, before re-reading this doc and `deploy-events-module.ps1` (whose `git add` list already referenced a not-yet-created `20260827130000_events_brand_and_onetime_festivals` folder — a naming pattern only explainable by the same mistake having been caught and fixed once already) and catching it before it was committed. `20260824090000` was reverted (`git checkout`) back to its applied content; the brand-profile/one-time-festival change lives in `20260827130000_events_brand_and_onetime_festivals/migration.sql` instead, plus the matching fallback block in `ensure-all-columns.js`. If you're about to touch `20260824090000` or `20260825120000`'s `migration.sql` for any reason, stop — add a new migration folder instead.

## ⚠️ Railway never runs migrations at boot — this is deliberate, not a bug. Apply migrations by hand.

2026-08-25, part two: after the migration-checksum fix above shipped and deployed successfully, `Festival` queries kept 500ing with the *exact same* `P2022: Festival.month does not exist` error — now also breaking the History tab, since `EventSendLog`'s `festival: { select: { name: true } }` relation-select touches the same table. The Railway boot log showed the app starting up cleanly with zero output from `scripts/railway-migrate.js` at all — no "Checking recoverable migration", no `prisma migrate deploy` CLI output, nothing.

Cause: `backend/railway.json`'s `startCommand` is plain `"node dist/src/main.js"` — it does not run `scripts/railway-migrate.js` (or anything else) first. **This is intentional, not the bug.** On 2026-08-07 that startCommand was changed to `"node scripts/railway-migrate.js && node dist/src/main.js"` specifically to make schema drift self-heal automatically — and every deploy after that hung/failed with a 502, because the ~40-47s the migrate step takes ate into Railway's boot/healthcheck budget and the container got killed before the app's own first log line ever printed. Reverting `startCommand` back to plain `node dist/src/main.js` fixed it (confirmed 2026-08-08), and it must stay that way. **Do not put `railway-migrate.js` (or `prisma migrate deploy`, or `ensure-all-columns.js`) into `backend/railway.json`'s `startCommand` again** — this has already caused a full production outage once. (This incident is also recorded in project memory as `feedback_railway_no_migrate_at_boot`; a nearly identical near-miss happened again in this exact investigation before being caught and reverted.)

The consequence: **every schema change needs its migration applied by hand, from a local machine, against production**, before or after pushing — pushing code alone never applies it. Workflow: get the production `DATABASE_URL` from Railway's Postgres service → Variables tab, set it as `$env:DATABASE_URL` in PowerShell, then from `backend/` run `node scripts/railway-migrate.js` (resolves any recoverable-migration drift, runs `prisma migrate deploy`, then runs `ensure-all-columns.js` as a raw-SQL fallback). `deploy-events-module.ps1`'s step 3 does exactly this when `DATABASE_URL` is set, and warns loudly and skips if it isn't — it does not silently assume Railway will handle it. A `Festival` date→month/day repair block was also added to `ensure-all-columns.js` as the same belt-and-suspenders fallback every other column in that file already has, in case `_prisma_migrations` drifts on this table again in the future.

**If a future migration ever appears to silently not apply in production: this is normal and expected here, not a new bug** — go run `node scripts/railway-migrate.js` locally against production `DATABASE_URL`. Don't try to "fix" it by wiring migrations back into `startCommand`. (The repo-root `railway.json`, separately, sets an unrelated `uvicorn`/Python `startCommand` — almost certainly stale/leftover from something else, not applicable to this Node backend; left untouched since it wasn't the cause.)

## Files

- `backend/prisma/schema.prisma` — `EventOccasionType`, `EventSendStatus` enums; `EventFlyerTemplate`, `EventPerson`, `Festival`, `EventBrandProfile`, `EventSendLog`, `EventClientBusiness`, `EventClientWishLog` models. Migrations: `backend/prisma/migrations/20260824090000_add_events_module/` (base tables) + `20260825120000_events_recurring_festivals/` (Festival date→month/day) + `20260827130000_events_brand_and_onetime_festivals/` (Festival.isRecurring/oneTimeDate + EventBrandProfile table) + `20260828100000_events_client_wish_cards/` (CLIENT_FESTIVAL enum value, Festival.clientTemplateId, EventClientBusiness + EventClientWishLog tables).
- `backend/src/events/events.service.ts` — CRUD for templates/people/festivals/brand profile/**client businesses**, plus `renderAndSend()`/`renderAndSendClientWish()` (each shared by the scheduler and its own manual test-send), `loadBrandForRender()`/`loadClientForRender()`, and the signed public-URL logic (shared by both flows — `getFlyerImageForPublicRoute` checks `EventSendLog` then `EventClientWishLog`).
- `backend/src/events/events-scheduler.service.ts` — the daily `@Cron` job (`EVERY_DAY_AT_8AM`, `Asia/Kolkata`), matching both recurring (`matchesMonthDay`) and one-time (`matchesOneTimeDate`) festivals. `sendFestivals()` has two independent branches per festival: own-customer (`templateId`) and client-wish-card (`clientTemplateId`). Separate file from the CRUD service on purpose.
- `backend/src/events/flyer-render.ts` + `fonts.ts` — sharp/SVG compositing; `flyer-render.ts` also defines `FlyerFieldType`/`BrandKey`/`ClientKey` (shared by the frontend's mirrored types).
- `backend/src/events/events.controller.ts`, `events.module.ts` — routes under `/events/...`, registered in `app.module.ts`; includes `GET`/`PATCH /events/brand-profile` and the `/events/client-businesses/...` + `/events/client-wish-logs` routes.
- `frontend/app/events/page.tsx` — People / Templates (called "Flyer Templates" via `?occasionType=`) / **Brand** / **Client Businesses** / Festivals / History tabs. Nav entry in `dashboard-shell.tsx` (`PartyPopper` icon).
- `backend/src/whatsapp/whatsapp.service.ts` — `sendEventWish()` and `sendClientWishReady()` (separate AiSensy campaigns — see the decisions above).
- `docs/Events_Module_Client_Wish_Cards_Build_Prompt.md` — the original detailed build spec this feature was implemented from; read it for the full rationale/data-model/open-decisions if this summary isn't enough.

## Deployment

Code is deployed (Vercel frontend + Railway backend, both auto-deploy on push to `main`). Migrations are **not** applied by that auto-deploy — see the section above — so all four pending migrations (`20260824090000`, `20260825120000`, `20260827130000`, `20260828100000`) need `node scripts/railway-migrate.js` run by hand against production `DATABASE_URL` (from a local machine; no `railway` CLI available in this sandboxed session, so this session can never apply them itself). After that, follow `docs/Events_Module_Setup.md` for the things that live outside this repo: creating+approving the shared AiSensy template and setting `AISENSY_EVENTS_CAMPAIGN` / `BACKEND_PUBLIC_URL` in Railway (§1–2), and separately creating+approving the client-wish-card AiSensy template and setting `AISENSY_CLIENT_WISH_CAMPAIGN` (§3). Before trusting the automatic daily job, use the People tab's "send test" button and the Client Businesses tab's "Test" button on a real number first.
